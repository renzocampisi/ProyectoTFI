PatrónAplicación
Controller → Service Toda la lógica (armar el prompt, clasificar por stock, orquestar la confirmación) vive en armado.service.js. El controller solo lee req.body y delega.
Composición sobre servicios existentes El service nuevo no escribe una sola query propia de negocio: compone obras.create, presupuestos.create + addInsumo, remitos.create + addMaterial, compras.create y materiales.create. Todos ya validan lo suyo.
Validar todo antes de escribir Mismo criterio que kits.agregarARemito: se chequea disponibilidad de todas las líneas antes de insertar ninguna, para no dejar un remito a medio armar si una falla.
Adapter de Gemini, sin tocar panel/provider.js ya acepta responseSchema desde Scan & Match. Se usa tal cual — cero cambios en el adapter esta vez.
Hook por módulo useArmado encapsula los llamados a api.* y la máquina de pasos del asistente. El componente no llama a api directo.
CSS Modules Un .module.css por página/componente, sin estilos inline para layout.

Riesgos puntuales

  • El catálogo entero va en el prompt. En Scan & Match el universo eran los pocos ítems de una orden; acá son todos los materiales. Hoy son ~21 y entran cómodos, pero si crece a cientos el prompt se infla y el matcheo empeora. Se manda completo con un tope (~200); pasado eso, hay que prefiltrar por palabras del texto antes de llamar al modelo. Queda documentado como límite conocido, no se resuelve ahora.
  • presupuesto_insumos exige precio_unitario. No lo tenemos del texto dictado. Se resuelve con materiales.getPrecioReferencia() —que ya existe y devuelve el precio de la última compra o el de referencia— y cae a 0 si el material nunca se compró. El usuario lo corrige en el presupuesto, que ya permite editarlo.
  • Carrera entre proponer y confirmar. El stock puede cambiar entre que se arma la propuesta y que se confirma. addMaterial revalida y falla, pero si eso pasa a mitad de la carga el remito queda incompleto. Por eso la confirmación revalida todas las líneas antes de insertar la primera.
  • Un remito nuevo necesita responsable. El wizard no lo pide. Se usa el mismo placeholder que ya usa la RPC de aprobación de presupuestos ('-- por completar --'), para que ambos caminos se comporten igual y el usuario lo complete después en el detalle.
  • Una orden de compra exige proveedor. Resuelto en la revisión con un selector que incluye "decidir después": sin proveedor no se crea la orden, solo se listan los faltantes en pantalla.

Pasos ordenados

Backend
1Service de armado 📄 fieldstock-backend/src/services/armado.service.js nuevo

interpretar({ texto, destino }): lee el catálogo de materiales, arma el prompt con esa lista como universo de candidatos, llama a Provider.chat con responseSchema (líneas con descripción, cantidad, unidad, material sugerido y nivel de confianza). Si destino === 'REMITO', clasifica cada línea por stock — completo / parcial con el corte / faltante — y si es 'PRESUPUESTO' las devuelve todas sin clasificar. Defensivo igual que Scan & Match: un materialId alucinado que no esté en el catálogo se trata como "sin match".

confirmar(payload): revalida todas las líneas, resuelve la obra (usa la existente o crea una), y según el destino compone los servicios existentes. Devuelve los ids creados.

Verificación: tests unitarios mockeando el provider y los services (mismo estilo que scanMatch.service.test.js). Casos: destino presupuesto, destino remito con split parcial, material inexistente, obra nueva, y el rechazo cuando el stock cambió.
2Controller 📄 fieldstock-backend/src/controllers/armado.controller.js nuevo

Thin, dos handlers: interpretar y confirmar.

3Rutas 📄 fieldstock-backend/src/routes/index.js

POST /armado/interpretar y POST /armado/confirmar, ambas con requireRole(ROLES_OPERATIVOS) — mismo criterio que Scan & Match: dispara una llamada paga a Gemini y puede crear obras, materiales y órdenes de compra.

Verificación: npm test --prefix fieldstock-backend en verde (280 actuales + los nuevos).
Frontend
4Service HTTP 📄 fieldstock-frontend/src/modules/m-armado/services/armado.service.js nuevo

Dos métodos. interpretar con timeoutMs: 60_000 — el default de 15s no alcanza para una llamada a Gemini, lección de la feature anterior.

5Hook del asistente 📄 fieldstock-frontend/src/modules/m-armado/hooks/useArmado.js nuevo

Máquina de pasos: obra → destino → describir → interpretando → revision → confirmando → exito. Guarda el contexto elegido, las líneas propuestas y expone las funciones para editarlas.

6Página del asistente 📄 fieldstock-frontend/src/modules/m-armado/pages/ArmadoPage.jsx + .module.css nuevo

Página (no modal): son cuatro pasos y una tabla de revisión de varias líneas, necesita el ancho. Paso 3 incluye el botón de dictado usando la API de voz del navegador, con degradación silenciosa a solo texto donde no esté disponible. Paso 4 reusa la forma de tabla editable de ScanMatchModal, agregando la columna de destino de cada línea (remito / comprar) cuando corresponde.

Verificación: npm run dev y recorrer el asistente completo con una obra real, en los dos destinos.
7Ruta y acceso 📄 fieldstock-frontend/src/routes/AppRouter.jsx · src/layouts/AppLayout.jsx

Ruta /armado. En el sidebar entra en OPERATIVO_ITEMS, junto a Remitos y Obras, que es donde encaja conceptualmente. Título visible "Kits de Montaje"; la carpeta se llama m-armado para no confundirla con el módulo m-kits que ya existe y es otra cosa.

Verificación final: crear un presupuesto por dictado, aprobarlo, y confirmar que el remito se generó solo con esos materiales — o sea, que el puente que ya existía sigue funcionando con lo que produce esta feature.

Login con segundo factor por mail

Implementación — arquitectura aprobada en architecture.html

Preguntas abiertas — resueltas con los defaults propuestos

  • Vida del código: 10 minutos (setting de Supabase).
  • Freno a fuerza bruta: se incluye un límite simple de intentos por mail+IP en el endpoint de login (en memoria, por instancia).
  • Reenvío: botón "Reenviar código" con cuenta regresiva de 60 s; sin límite horario visible extra (Supabase ya frena por debajo de ~60 s).

Si querés otro número o sacar el rate-limit de esta tanda, decilo antes de arrancar.

Patrones de diseño

  • Controller → Service: toda la lógica (rate-limit, verificar contraseña, decidir por rol, disparar el código) vive en auth-login.service.js. El controller solo lee req.body / req.ip y responde { data }.
  • Cliente Supabase dedicado y sin estado: se agrega config/supabaseAuth.js con la anon key y persistSession:false. El cliente service-role compartido (config/supabase.js) no se toca. Mismo criterio de aislamiento que ya separa frontend (anon) de backend (service).
  • Hook de auth como único punto de entrada: useAuth gana verificarCodigo() y su signIn() pasa a hablar con nuestro backend en vez de con Supabase directo. Los componentes no llaman a api ni a supabase.auth por su cuenta — igual que hoy.
  • Extensión aditiva de contrato: POST /auth/login responde { session } o { requiereCodigo:true }. El resto de la app (guard de rutas, requireAuth, RLS) no cambia — solo cambia cuándo aparece la sesión.
  • CSS Modules: el paso de código se agrega al LoginPage.module.css existente, sin estilos inline de layout.
  • Anti-enumeración: se mantiene el mensaje genérico único de LoginPage para email/contraseña incorrectos.

Pasos ordenados — Backend

1. Cliente Supabase para auth (anon, sin persistir) nuevo · fieldstock-backend/src/config/supabaseAuth.js · fieldstock-backend/.env · Fly secret Agregar SUPABASE_ANON_KEY al .env del backend (es la misma que ya usa el frontend, es pública) y como secret en Fly (flyctl secrets set). El nuevo módulo exporta supabaseAuth = createClient(url, anonKey, { auth: { persistSession:false, autoRefreshToken:false } }) y falla-fast si falta la var, igual que config/supabase.js.
Verificación: el backend arranca sin error; import del módulo no rompe.
2. Service de login nuevo · fieldstock-backend/src/services/auth-login.service.js login({ email, password, ip }):
  1. Chequear el rate-limit (paso 3). Si excede → Error con status 429.
  2. supabaseAuth.auth.signInWithPassword({ email, password }). Si error → registrar el intento y tirar Error('Email o contraseña incorrectos') con status 422 (no 401: api.js del frontend trata cualquier 401 como sesión expirada y dispara logout + redirect; acá el login todavía no tiene sesión, un rechazo es 422). La sesión que devuelve NO se persiste; queda en una variable local.
  3. Leer el perfil: supabase.from('usuarios_resumen').select('id, role, activo').eq('id', user.id).maybeSingle(). Sin perfil o activo:false → status 422 (mensaje "Cuenta desactivada" para el segundo caso, mismo tono que requireAuth).
  4. Si role === ROLES.ADMIN → devolver { session: { access_token, refresh_token } } (de la sesión efímera del paso 2).
  5. Si no → supabaseAuth.auth.signInWithOtp({ email, options: { shouldCreateUser:false } }). Si error → Error('No pudimos enviar el código. Reintentá en un momento.') con status 502. Si ok → devolver { requiereCodigo:true, email }.
Verificación: test unitario (paso 12).
3. Límite de intentos (en memoria) fieldstock-backend/src/services/auth-login.service.js (interno) Un Map a nivel de módulo: clave `${email.toLowerCase()}|${ip}`, valor = array de timestamps de los últimos 10 min. En cada intento se podan los viejos y se agrega el actual; si el array supera 5 → status 429. Cuenta todos los intentos (ok y fallidos) para topear también el abuso de envío de código.
Verificación: el 6º intento seguido para el mismo mail+IP devuelve 429 (cubierto en el test).
4. Controller fieldstock-backend/src/controllers/auth-publico.controller.js Nueva función login(req, res, next): toma email / password de req.body e ip de req.ip, llama a AuthLoginService.login(), responde res.json({ data }). Errores vía next(err) — el errorHandler global ya los formatea.
Depende del paso 2.
5. Ruta fieldstock-backend/src/routes/index.js router.post('/auth/login', AuthPublicoCtrl.login) en el bloque público, antes de router.use(requireAuth) (línea ~90). express.json() global ya corre antes, así que req.body llega parseado.
Verificación: curl con creds inválidas → 401 genérico; con las del ADMIN → { data: { session } }; con las de un no-ADMIN → { data: { requiereCodigo:true } } y llega el mail.

Pasos ordenados — Frontend

6. Hook de auth fieldstock-frontend/src/shared/hooks/useAuth.jsx
  • signIn(email, password) pasa a api.post('/auth/login', { email, password }). Si la respuesta trae session → await supabase.auth.setSession(session) (dispara onAuthStateChange → cargarPerfil) y devuelve {}. Si trae requiereCodigo → devuelve { requiereCodigo:true }. Error → { error: { message } } (se mantiene el withTimeout defensivo).
  • Nuevo verificarCodigo(email, codigo) → supabase.auth.verifyOtp({ email, token: codigo, type:'email' }) envuelto en withTimeout. Devuelve { error } o {}.
  • Ambos se exponen en el value del context. signOut queda igual.
Depende de los pasos 2 y 5.
7. Página de login — dos pasos fieldstock-frontend/src/modules/m0-auth/pages/LoginPage.jsx
  • Estado nuevo: paso ('credenciales' | 'codigo'), codigo, y una cuenta regresiva de reenvío.
  • Submit de credenciales: llama signIn. Si requiereCodigo → setPaso('codigo') y arranca la cuenta de 60 s. Si hay session → el <Navigate> de arriba (o navigate('/')) hace el resto. Error → mensaje genérico.
  • Paso "código": input único inputMode="numeric" autoComplete="one-time-code" maxLength=6; botón "Verificar" → verificarCodigo; error → "El código no es válido o venció."; éxito → navega.
  • "Reenviar código (Ns)": deshabilitado mientras la cuenta > 0; al tocarlo re-llama signIn(email, password) (la contraseña sigue en estado) y reinicia la cuenta.
  • "Volver": setPaso('credenciales'), limpia codigo y password.
  • "¿Olvidaste tu contraseña?" solo en el paso 1. Se conserva el botón "Limpiar sesión y reintentar".
Depende del paso 6.

Riesgos puntuales

Sesión "a medias" — imposible por diseño. La contraseña se valida en el backend y su sesión se descarta ahí mismo; el cliente solo obtiene sesión vía verifyOtp. No queda ningún estado intermedio reusable si se cierra la pestaña entre un paso y el otro.
Template del mail. Si "Magic Link" queda con {{ .ConfirmationURL }} el usuario recibe un enlace y el código tipeado no valida. El paso 11 es bloqueante y se prueba con un login real antes de dar por cerrada la feature.
Rate-limit en memoria. Se reinicia en cada deploy y es por-máquina (Fly corre una sola). Alcanza para la escala descrita en CLAUDE.md; si en el futuro hay varias instancias, mover a una tabla o a Redis.
Anon key en el backend. Es pública (el frontend ya la expone). Usar la service key para el endpoint /token sería peor; por eso se agrega la anon key con un cliente sin persistencia y no se toca el cliente service-role compartido.
Sin migración de schema. Revertir la feature es volver los commits de front y back; el SMTP y el template configurados quedan pero son inofensivos, y el login vuelve solo a un paso.

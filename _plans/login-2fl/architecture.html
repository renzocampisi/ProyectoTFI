Login con segundo factor por mail

Para todos los roles salvo ADMIN: contraseña correcta → código de un solo uso al mail → recién ahí se abre la sesión.

Flujo

flowchart TD
  A["Pantalla de login\nemail + contraseña"] --> B["El backend verifica la contraseña\n(sesión efímera, no se guarda)"]
  B -->|contraseña incorrecta| C["Error genérico\n'credenciales incorrectas'"]
  B -->|correcta| D{"¿Rol ADMIN?"}
  D -->|sí| E["El backend devuelve la sesión\n→ entra directo, como hoy"]
  D -->|no| F["Supabase Auth manda un código\nde 6 dígitos al mail del usuario"]
  F --> G["Pantalla de código\n(reenviar / volver)"]
  G --> H["Supabase Auth valida el código"]
  H -->|correcto| I["Sesión creada\n→ se abre la app"]
  H -->|incorrecto / vencido| J["Error, permite reintentar\no pedir uno nuevo"]
  J --> G
  C --> A

El problema

Hoy cualquier usuario entra con solo email + contraseña. Las contraseñas de los empleados son autogeneradas y se muestran una vez en un modal — fáciles de filtrar, reenviar o dejar anotadas. Se quiere que, además de la contraseña, haya que probar acceso al mail de la cuenta en cada inicio de sesión. El ADMIN queda como está (cuenta de pruebas).

La forma

Tres responsabilidades, todas sobre piezas que ya existen:

  • Pantalla de login — pasa de un paso a dos: primero email + contraseña; si la cuenta necesita código, aparece un segundo paso para tipear los 6 dígitos, con opción de reenviar y de volver atrás. El ADMIN nunca ve el segundo paso.
  • El backend — gana un único punto de entrada de login. Verifica la contraseña contra Supabase sin quedarse con esa sesión, mira el rol, y decide: ADMIN entra directo; cualquier otro rol dispara el envío del código y responde "código enviado" sin entregar todavía ninguna sesión.
  • Supabase Auth — es quien genera el código, lo guarda hasheado, lo manda por mail, controla su vencimiento y su límite de reenvíos, y crea la sesión cuando el código ingresado es correcto. El mail sale por el SMTP de Supabase, configurado para usar Resend (el mismo proveedor que ya manda los comprobantes de pago).

El resto del sistema no cambia: una vez que hay sesión, useAuth, el guard de rutas, requireAuth en el backend y las políticas de Supabase funcionan igual que hoy. La única diferencia es cuándo aparece esa sesión.

Por qué así y no de otra manera

OpciónQué implica
Código nativo de Supabase + Resend como su SMTP (elegida) Supabase hace el trabajo pesado: generación, hash, vencimiento, límite de reenvío y creación de sesión. El backend solo verifica la contraseña y decide si hace falta código. menos código
Código propio en el backend Tabla de códigos, endpoints de pedir/verificar, y pegado manual para crear la sesión. Control total del mail y las reglas, a cambio de más superficie que mantener y asegurar. más superficie
Proveedor de auth externo (Auth0 / Clerk free) Reemplaza Supabase Auth, que está cableado en el guard de rutas, en requireAuth y en las políticas de la base. Reescritura grande para un objetivo acotado. descartada

La contraseña se verifica en el backend y no en el navegador a propósito: así el cliente nunca llega a tener una sesión "a medias" (contraseña OK pero código pendiente) que alguien pudiera reusar reabriendo la pestaña. La única sesión que existe del lado del cliente es la que nace después del código.

Decisiones tomadas

  • Segundo factor, no passwordless. La contraseña sigue siendo el primer factor; el código se suma como segundo paso obligatorio.
  • Alcance por rol, regla fija. ADMIN entra con contraseña como hoy. DUEÑO, ENCARGADO y OPERARIO pasan siempre por el código. Sin pantalla de configuración.
  • El mail sale por Resend, a través del SMTP de Supabase Auth — no se agrega un canal de mail nuevo.
  • Un solo punto de entrada de login en el backend: el frontend no necesita saber el rol de antemano, lo resuelve el backend después de validar la contraseña.
  • Mensaje de error genérico ante email o contraseña incorrectos — se mantiene el criterio anti-enumeración que ya usa el login actual.

Qué NO hace esta feature

  • No toca el login del ADMIN.
  • No elimina las contraseñas ni cambia cómo se dan de alta los usuarios.
  • No agrega app de autenticación (TOTP), SMS, ni "recordar este dispositivo" — cada inicio de sesión pide código.
  • No agrega una pantalla para administrar o ver códigos; son efímeros y no se listan en ningún lado.
  • No cambia nada de la sesión ya iniciada: expiración, refresco y cierre de sesión siguen igual.

Preguntas abiertas

1. ¿Cuánto vive el código? Propongo 10 minutos (Supabase trae 1 hora por defecto; para un segundo factor 10 min es más sano). ¿Te sirve ese número?
2. Freno a la fuerza bruta de contraseña. El punto de entrada de login conviene que tenga un límite de intentos por mail/IP (hoy el proyecto no tiene ninguno). ¿Lo incluimos en esta feature o lo dejamos para después?
3. Reenvío del código. La pantalla de código va a tener un botón "reenviar" con una cuenta regresiva (Supabase no deja reenviar antes de ~60 s). ¿Alcanza con eso o querés además un límite de "pedidos por hora" visible para el usuario?

Patrones de diseño

  • Controller → Service, sin excepción: toda la lógica nueva (leer/escribir vocabulario, armar el prompt con foto) vive en los services. El controller gana una responsabilidad puntual — distinguir si vino req.file o no — mismo alcance que ya tiene scanMatch.controller.js al extraer buffer/mimetype.
  • Multer memoryStorage condicional: mismo patrón exacto que /compras/:id/scan-match y /compras/:id/comprobante — multer({ storage: memoryStorage(), limits: { fileSize } }).single(campo). La diferencia es que acá se monta sobre una ruta que hoy ya recibe JSON puro; multer solo actúa si el Content-Type es multipart, así que el caso existente (sin foto) sigue exactamente igual.
  • Hook por módulo: useArmado.js gana el estado de la foto y arma el FormData cuando corresponde — mismo criterio que ya usa compras.service.js para scanMatchProponer. El componente sigue sin llamar a api directo.
  • Extensión aditiva de contrato: tanto el responseSchema de Gemini como el payload de POST /armado/confirmar suman campos opcionales (advertenciaFoto, materialIdPropuesto). Nada de lo que ya existe cambia de forma — los tests actuales de armado.service.test.js siguen pasando sin tocarlos.
  • Sin ORM, sin RLS manual: el vocabulario aprendido es una tabla más leída con el SDK de Supabase directo. No lleva empresa_id — el sistema es single-tenant por instancia (confirmado en auth-publico.service.js: "sin empresa_id"), así que el aislamiento por empresa que pedía la arquitectura ya viene gratis: cada cliente tiene su propia base.

Riesgos puntuales

Orden de middlewares en la ruta dual JSON/multipart

Para que POST /armado/interpretar siga aceptando JSON puro (caso de hoy) Y multipart con foto (caso nuevo) en la misma URL, hace falta que express.json() global corra antes que el multer de esta ruta en la cadena de middlewares — así, ante un request JSON, multer ve un Content-Type que no le corresponde y no toca req.body. Confirmar el orden actual en routes/index.js antes de agregar el middleware; si hiciera falta, este multer se monta después del express.json() global, nunca antes.

Qué cuenta como "corrección" para el aprendizaje

Solo se graba en armado_vocabulario_aprendido cuando el material final de la línea difiere de materialIdPropuesto (la IA se equivocó y el usuario ajustó) o cuando la línea usó materialNuevo con un nombre bien distinto al texto. Si el usuario simplemente acepta lo que propuso la IA, no se graba nada — grabar aciertos no aporta señal y ensucia la tabla.

El registro de aprendizaje nunca bloquea la confirmación

registrarCorreccion() se llama en un try/catch aislado dentro de confirmar(): si falla (problema de red puntual con Supabase), se loguea y se sigue — el presupuesto o remito ya escrito no se pierde ni se revierte por esto.

Tope de vocabulario en el prompt

Mismo problema que ya documenta CAP_CATALOGO: si con el tiempo se acumulan muchas correcciones, no entran todas en el prompt. buscarRelevante() aplica un tope (mismo orden de magnitud que CAP_CATALOGO) filtrando por coincidencia simple de palabras entre el texto actual y texto_normalizado — no es búsqueda semántica, es una heurística de primera versión.

2Service de vocabulario aprendido 📄 fieldstock-backend/src/services/armadoVocabulario.service.js nuevo

buscarRelevante(texto, { limite }): normaliza el texto de entrada y devuelve las filas cuyo texto_normalizado comparte palabras con él, ordenadas por veces_confirmado descendente, topeadas a limite.

registrarCorreccion({ textoOriginal, materialId }): upsert — si ya existe una fila con ese texto_normalizado + materialId, incrementa veces_confirmado; si no, la crea con 1.

Verificación: test unitario mockeando el chain de config/supabase.js, mismo criterio que compras.service.test.js.
3Extender armado.service.js 📄 fieldstock-backend/src/services/armado.service.js

ARMADO_SCHEMA: cada línea suma advertenciaFoto (string, opcional, no entra en required).

construirPrompt(catalogo, { conFoto, vocabulario }): si conFoto, agrega el párrafo explícito — la imagen es apoyo y verificación, la cantidad y el tipo siempre salen del texto, nunca de lo dibujado. Si vocabulario.length, agrega una sección de "equivalencias ya confirmadas antes" con esos pares texto→material.

interpretar({ texto, destino, foto }): foto es opcional ({ buffer, mimeType }, mismo shape que ya usa Scan & Match). Llama primero a ArmadoVocabulario.buscarRelevante(texto), arma contents con una o dos parts según haya foto o no (mismo patrón que scanMatch.service.js). Cada línea de salida ahora también incluye materialIdPropuesto — el mismo valor que materialId en este momento, pero conservado aparte porque el usuario lo puede cambiar en la revisión y confirmar() necesita comparar ambos.

confirmar(payload): después de resolver cada línea (igual que hoy), si materialIdPropuesto difiere del material final, o la línea vino con materialNuevo, llama a ArmadoVocabulario.registrarCorreccion() dentro de un try/catch que solo loguea (ver riesgos).

Verificación: extender armado.service.test.js (ver sección Testing abajo).

El paso de contraseña corre siempre. Un dispositivo de confianza solo evita el segundo factor.

Problema

Hoy todo login de un rol no-ADMIN pide un código por mail, en cada inicio de sesión y en cada dispositivo. Para el uso diario —la misma persona en su mismo teléfono— es fricción pura, y además cada intento consume un envío de mail (que es justo lo que nos está frenando ahora). Queremos que el código se pida solo la primera vez que alguien entra desde un dispositivo nuevo. Después, ese dispositivo queda "de confianza" por un tiempo y el login vuelve a ser un solo paso: usuario y contraseña.

Enfoque

  • Qué es un "dispositivo". Un token opaco de alta entropía que emite el backend y que el navegador guarda localmente, en el mismo almacenamiento del navegador donde ya vive la sesión de Supabase. El backend guarda solo un hash del token, atado al usuario, con fecha de creación, fecha de último uso, vencimiento y una descripción legible del equipo derivada del user-agent. No se usa la IP ni un fingerprint del navegador como identidad — la descripción es solo cosmética, para reconocer la fila en la lista.
  • La contraseña no se toca. Se sigue verificando server-side en cada login, con su rate-limit. Lo único que un dispositivo de confianza saltea es el código. Es decir: en un equipo de confianza el login baja de dos factores a uno (la contraseña), nunca a cero.
  • En el login. Después de validar contraseña y rol, el backend mira si la request trae un token de confianza vigente para ese usuario. Si sí, devuelve la sesión directo —igual que hoy hace con el ADMIN— y corre la fecha de último uso. Si no, manda el código como ahora. Un token vencido o revocado se ignora y se cae al camino del código; el front descarta el token muerto.
  • Al verificar el código. En el paso del código hay un checkbox "Confiar en este dispositivo", tildado por default. Si quedó tildado, apenas el código se verifica con éxito el front le pide al backend —ya con sesión válida— que registre el equipo: el backend genera el token, guarda su hash y lo devuelve una sola vez. En una tablet compartida de obra, el usuario lo destilda y ese equipo nunca se recuerda.
  • Vigencia. Cada login por el camino corto renueva la confianza. El dispositivo expira si pasa 30 días sin usarse, o al llegar a 90 días desde que se creó, lo que ocurra primero.
  • Revocación. Cuatro vías: el propio usuario desde "Mi perfil"; el DUEÑO o ADMIN sobre un empleado desde el panel de Usuarios; automática al cambiar la contraseña o usar "recuperar contraseña"; y —de hecho— desactivar al usuario, que ya lo saca por requireAuth aunque el token siga existiendo.

Dónde encaja

  • Vive en el mismo endpoint público de login, más un endpoint nuevo autenticado para registrar el dispositivo. Sigue el patrón controller → service.
  • Suma una tabla nueva en Supabase para los hashes de token y sus metadatos, con su RLS propia. No toca usuarios ni dispositivos_rastreo (GPS, sin relación).
  • En el front: la pantalla de login (checkbox + envío del token al iniciar sesión) y "Mi perfil" (lista de equipos con último uso, botón de revocar). El panel de Usuarios suma la acción de revocar para DUEÑO/ADMIN.
  • El ADMIN no se ve afectado: ya entra directo, nunca pasa por el segundo factor.

Formas candidatas

A · Token opaco con registro en base Recomendada

El backend emite un token aleatorio, guarda su hash y metadatos en una tabla. Cada login corto lo valida contra esa tabla.

Revocación individual real e inmediata.

Habilita la lista de "mis dispositivos" con último uso y descripción.

El control del DUEÑO/ADMIN sobre los equipos de un empleado sale natural.

Una query más por login. Irrelevante a esta escala.

B · Token firmado sin estado

El backend firma un token con el id de usuario y un vencimiento; no guarda nada y lo valida por firma.

Cero queries, cero tabla.

Para revocar un equipo puntual hace falta, igual, una tabla de revocados — media Forma A pero peor.

No hay dónde guardar "último uso" ni descripción: no existe la lista de dispositivos que pediste.

C · Estirar la sesión de Supabase

No distinguir equipos: alargar la vida del refresh token para que la sesión casi nunca caduque.

Cero desarrollo.

No distingue "dispositivo nuevo" — no resuelve el problema planteado.

Cualquier cierre de sesión obliga a rehacer el 2FA. Sin control granular.

Recomendación: Forma A. Es la única que sostiene la gestión de dispositivos y la revocación por parte del DUEÑO que elegiste.

Límites — lo que esta feature no hace

  • No reemplaza ni debilita el paso de contraseña.
  • Recuerda dispositivos, no usuarios: si en el mismo navegador entran dos empleados, cada uno marca su propio equipo de confianza (el token está atado al usuario).
  • No usa IP ni fingerprint como identidad.
  • No aplica al ADMIN.
  • No agrega un "recordarme" para la contraseña — se sigue tipeando usuario y contraseña en cada login.

Decisiones ya tomadas

Marcado del equipo: checkbox "Confiar en este dispositivo" tildado por default en el paso del código.

Gestión: autogestión desde "Mi perfil" + el DUEÑO/ADMIN puede revocar los equipos de un empleado desde Usuarios.

Duración: 30 días de inactividad, con tope duro de 90 días desde la creación.

Supuestos que tomo como dados (vetalos si no van): cambiar o recuperar contraseña revoca todos los equipos de ese usuario; la descripción del equipo se deriva del user-agent y es solo informativa.

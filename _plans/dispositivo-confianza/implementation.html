Persistencia

La vigencia se calcula, no se guarda: una fila está vigente si revocado_at IS NULL y ultimo_uso > now() - 30 días y created_at > now() - 90 días. RLS habilitada sin políticas — el backend entra con SUPABASE_SERVICE_KEY, mismo criterio que el resto de las tablas de negocio.

Patrones a aplicar

  • Controller → Service. Toda la lógica (generar token, hashear, validar vigencia, revocar) vive en un service nuevo dispositivos-confianza.service.js. El auth-login.service lo compone — le pide "¿este token es válido para este user?" y actúa según la respuesta. Mismo estilo que armado.service orquestando sub-services.
  • Errores y respuestas. err.status + throw para fallos; res.json({ ok: true, data }) en éxito. Un deviceToken inválido no es error — se ignora en silencio y se cae al código.
  • Hash como el de una contraseña. El token crudo (32 bytes aleatorios, base64url) nunca se guarda: en la tabla va sha-256 hex. Se usa node:crypto, sin dependencias nuevas.
  • Hook por módulo + api.js. Frontend: un dispositivosConfianza.service.js en m0-auth que envuelve api.*; los componentes no llaman api directo. El token local se maneja en un util al lado de supabaseClient.js.
  • CSS Modules. El checkbox del login y la sección nueva de "Mi perfil" usan los .module.css ya existentes de esas páginas.
  • RLS + migración fechada. Archivo en _sql/migrations/2026_09_09_dispositivos_confianza.sql aunque se corra a mano en el editor de Supabase (sugerir ese nombre para guardarlo).

Riesgos puntuales de este cambio

  • El logout no debe borrar el token de confianza. clearSupabaseStorage() borra todo lo que empieza con sb-; el token de dispositivo va con prefijo distinto (fs-trusted-device) y queda intacto en logout y en el on401() de api.js. Solo lo borra una revocación explícita.
  • El cambio de contraseña ocurre fuera del backend. Va por supabase.auth.updateUser en RestablecerPasswordPage. La revocación de todos los dispositivos se dispara desde ahí, con el JWT de recovery todavía válido, antes del signOut(). Si el usuario cierra la pestaña antes, no se revoca — mitigado porque "Mi perfil" tiene "revocar todos" manual.
  • Token robado = 2FA degradado a 1FA para ese user en ese equipo hasta que venza o se revoque. Es exactamente la intención de la feature; la contraseña se sigue exigiendo siempre. No hace falta atar el token al user-agent (rompe con cada update del navegador).
  • Un navegador, dos empleados. El token está atado a usuario_id; si en el mismo equipo entra otra persona, su login no matchea y recibe código. Correcto.
  • Rollback. Es revertir los commits de front y back; la tabla queda pero es inofensiva. Sin cambio de firma en RPCs ni en vistas (usuarios_resumen no se toca).

4. Controller + rutas. fieldstock-backend/src/controllers/auth-publico.controller.js · dispositivos-confianza.controller.js · routes/index.js
  • login ctrl: pasar req.body.deviceToken al service.
  • POST /auth/dispositivos-confianza — requireAuth, cualquier rol. Lee req.headers['user-agent'], llama registrar, devuelve { id, token }.
  • GET /auth/dispositivos-confianza — requireAuth — lista los del req.user.id.
  • DELETE /auth/dispositivos-confianza/:id y DELETE /auth/dispositivos-confianza — requireAuth — revocan uno / todos, siempre WHERE usuario_id = req.user.id.
  • DELETE /usuarios/:id/dispositivos-confianza — requireRole(ROLES_ADMIN_LEVEL) — revoca todos los del empleado :id. Va junto a las otras rutas de /usuarios/:id.

curl a cada endpoint con un JWT real; login con y sin deviceToken en el body.
